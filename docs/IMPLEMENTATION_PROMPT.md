## 絶対に守ること
- 仕様書の「決定事項 D-01〜D-12」は変更しない。変更が必要だと思ったら、実装を止めて理由を私に確認する(勝手に直さない)。
- 定数名・型名・関数名は仕様書の表記どおりにする(テストとテストフック `window.__HANG__` が依存する)。
- ゲームロジック(`src/logic/`)は純粋関数にする。three / DOM / window / `Math.random` / `Date.now` / localStorage を参照しない(`purity.test.ts` で検証)。GameState はイミュータブル。
- 駒の移動アニメーションは 1 手全体で 0.8 秒(`MOVE_DURATION_MS = 800`、許容 0.7〜0.9 秒)。2 マス動く場合も分割しない。
- アニメーション中は入力をすべて無視する。
- 盤面は 3D 俯瞰(Three.js)。1 コードベースで Windows(Electron)/ iOS・Android(Capacitor)/ PWA に届く構成にする。ただし実機ビルド(exe / APK / IPA)はこのコンテナでは行えないので、設定ファイルと `vite build` の成功までを目標にする。
- 完了していないものを「できた」と報告しない。テストが落ちたら、落ちた事実と出力をそのまま報告する。テストをスキップ・削除して緑にしない。

## 技術スタック(決定済み)
TypeScript(strict)+ Three.js + Vite、UI は素の DOM + CSS(フレームワーク不使用)、単体テストは Vitest、E2E は Playwright(コンテナにインストール済みの Chromium と同じバージョンを使う。`playwright install` はしない)。起動オプション `--use-angle=swiftshader --enable-unsafe-swiftshader` が必要。コマンドは仕様 2.4 のとおり。

## 実装の進め方
仕様 11 章のマイルストーン M0 → M9 の順に進める。各マイルストーンの区切りで次を確認してからコミットする。
1. `npx tsc --noEmit` が通る
2. `npm test`(Vitest)が通る
3. 画面に関わる変更は、実際に Playwright でスクリーンショットを撮り、自分の目で確認する(盤が見切れていないか、HUD と重なっていないか等)

M1〜M3(ロジック)は先に作り込み、単体テストを仕様 10.1 の全ケース分書く。ロジックが固まる前に 3D 描画へ進まない。ランダムプレイで 2 人戦・3 人戦を各 20 局以上最後まで進められること(無限ループしないこと)も確認する。

## 見た目・操作の要件(仕様 7 章に加えて)
- 背景は「海賊船の船室で、雑多な財宝が置かれた木の卓の上で遊んでいる」雰囲気にする。板張りの卓、船室の内壁と丸窓、吊りランタン、宝箱と金貨、ろうそく、ラム酒の瓶、宝の地図、どくろ、短剣、羅針盤、金の杯、ロープ、樽などを手続き生成で置く。盤の視認性が最優先で、小物が盤に重ならないこと。
- 手番が替わるたびに(配置フェーズ含む)、画面上部中央に「プレイヤーNのターン」のバナーを約 0.9 秒、弾むように表示する。入力はブロックしない。
- 「確定」ボタンは盤面の下部中央に大きく目立つように置く。押せるときは目立つ演出(光の明滅など)をつける。**拡大・移動のアニメで脈動させない**(Playwright が「要素が安定していない」と判定してクリックできなくなる)。
- 縦長・横長のどちらでも盤が見切れず、HUD とキャンバスが重ならないこと(360×640 / 390×844 / 844×390 / 1280×720 / 1920×1080 で確認)。

## 検証でハマりやすい点(経験済み)
- コンテナの描画はソフトウェア(SwiftShader)で、フレームレートが 10 fps 前後まで落ちる。E2E の個別テストのタイムアウトは長め(120 秒程度)にし、アニメ時間の許容範囲はフレーム 1 枚分(約 150ms)広げる。実機の性能を示すものではないと報告に書く。
- 描画コストを抑えるため、同じ形の小物(金貨など)は InstancedMesh にまとめ、床・壁などの広い面には軽いマテリアル(Lambert)を使う。
- 長いコマンド(全 E2E など)はバックグラウンド実行にして、完了通知を待つ。`sleep` で待たない。
- 結果のスクリーンショットは `test-results/` に保存し、目視で確認する。

## 完了の定義
- `npm test` と `npm run build` が通る。
- `npm run test:e2e` が desktop / mobile-portrait / mobile-landscape の 3 プロジェクトで通る(E1〜E13)。
- 2 人戦・3 人戦のそれぞれで、配置 → 移動 → 壁 → 壁破り → 終了 → 結果表示 → 「もう一度」「タイトルへ」まで手動操作と同等の流れが通る。
- `game/README.md` に起動・テスト・ビルド・パッケージング手順を書く。
- 最後に、未実施のもの(実機ビルド、実機での動作確認、効果音・CPU 対戦などのスコープ外)を正直に一覧にして報告する。

- 仕様の曖昧点や矛盾を見つけたら、実装を進める前にここで質問する。軽微なもの(命名、内部構造)は自分で決めてよい。
